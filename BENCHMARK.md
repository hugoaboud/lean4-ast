# Benchmark: JSON round-trip vs. reading Lean's heap

The library used to hand Lean's syntax tree to Rust as JSON: the Lean wrapper
walked the tree, built a `Json` value for every node, compressed it, copied a
20 MiB string through C, and Rust parsed it back into `Vec<Node>`. None of that
was the parser's work — it was an encoding of a tree that already existed in
memory. Now the tree crosses the FFI as `lean_object*` and Rust reads it where
Lean left it (`crates/lean4-ast/src/raw.rs`).

This file records what that was worth, with the harness and the file used, so it
can be reproduced.

## Method

| | |
| --- | --- |
| Machine | Intel i7-6500U, 4 threads, 7 GiB RAM, Linux/amd64 |
| Lean | `leanprover/lean4:v4.36.0-rc2` (its runtime is built with mimalloc) |
| Rust | rustc 1.99.0, `--release` |
| File | generated by the harness itself: `BLOCKS = 400` copies of a mix of declarations (structures, inductives, classes, `def`/`theorem` with `by` and `calc` blocks, `match`, `do`, lambdas, `syntax`/`macro`, attributes) |

```
source:            311,863 bytes · 14,418 lines
top-level nodes:   4,006 commands
syntax nodes:      272,601 (59,221 atoms, 35,617 identifiers)
syntax errors:     0
```

The file is generated in memory and parsed from there, so no large fixture is
committed; `cargo run --release --example bench -- --write Bench.lean` writes it
out if you want to look at it or feed it to another tool.

**"parse"** below is `parse()` of that source, after `init()` and after the
modules the parser needs are loaded: 5 rounds are timed and the median reported,
then the whole benchmark is repeated with the two builds alternating (the VM's
absolute speed drifts by up to 2× between sessions, so only runs measured
back-to-back are comparable — the **ratio** is what is stable).

Both harnesses hash everything they read — kind, span, text, missing flag, in
traversal order — and print the digest. Both print the same one:

```
digest 0xe9393e935e3879d4
```

so the two pipelines are measured on, and proved to produce, the same tree.

## Results

Same file, same machine, alternating builds, 3 pairs, medians:

| | before (JSON) | after (raw objects) | change |
| --- | --- | --- | --- |
| `parse`, median | **1.875 s** | **0.508 s** | −73 %, **3.7× faster** |
| `parse`, best round | 1.774 s | 0.484 s | 3.7× |
| full traversal of the tree | 48.4 ms | 38.2 ms | −21 % |
| `parse` + traversal | 1.923 s | 0.546 s | **3.5×** |
| bytes handed across the FFI | 20.5 MiB of JSON | 0 (a pointer) | — |
| peak RSS | 1,840 MiB | 1,511 MiB | −329 MiB (−18 %) |
| RSS while the tree is held | 1,820 MiB | 1,511 MiB | −309 MiB |

A second session, 5 pairs, same file: before 3.09–3.60 s, after 0.93–1.40 s, i.e.
2.5×–3.7× faster per pair (median 3.3×). The absolute numbers move with the
machine; the ratio does not.

### Scaling

One session, three sizes, both builds measured back to back (median of 5 rounds):

| source | nodes | JSON payload | before | after | ratio |
| --- | --- | --- | --- | --- | --- |
| 19,288 B (918 lines) | 17,226 | 1.27 MiB | 122 ms | 32 ms | 3.8× |
| 76,963 B (3,618 lines) | 68,301 | 5.07 MiB | 433 ms | 124 ms | 3.5× |
| 311,863 B (14,418 lines) | 272,601 | 20.54 MiB | 3,370 ms | 1,012 ms | 3.3× |

The JSON payload grows with the tree (a `{"kind":…,"span":[…],"text":…}` object
per node); the raw tree is the tree, so the only bytes that move are a pointer.

### Where the time goes now

Measured with temporary instrumentation in the C shim, on a run where `parse`
took 1.0 s:

| | |
| --- | --- |
| Lean's own parser (`parseHeader` + `parseCommand`) | ~960 ms |
| `lean_mark_mt`, which makes the tree safe to carry across threads | ~25 ms |
| the rest of the FFI (< 1 ms) | — |

`lean_mark_mt` is a single pointer walk over the object graph; it is what allows a
`ParseTree` to be moved to another thread and dropped there. It is 2–3 % of a
parse, and it replaced ~1.9 s of JSON.

Reading the tree is now the caller's choice and its own cost:

| read | cost |
| --- | --- |
| `short_kind()` on a node | a pointer chase (~ns); the name is already in Lean's heap |
| `text()` on an atom | the `String` Lean allocated — borrowed, not copied |
| full traversal (272,601 nodes, all fields) | 38 ms |
| `to_file_ast()`, copying the whole tree into owned `Node`s | 56–74 ms |

If you need no copy, you pay for the parse and nothing else: a caller that parses
a file and reads 5 % of it pays 5 % of 38 ms. The old pipeline always paid the
full 20.5 MiB, whether or not anything was read.

## Was the tree actually the same?

Dumping both trees to the same unambiguous text format and diffing them:

| file | nodes | differences in depth / span / missing / text |
| --- | --- | --- |
| generated benchmark file | 272,602 records | **0** |
| `Lean/Parser/Term.lean` | 13,484 | 2 records, both a doc-comment token whose *kind* the old renderer split across a line |
| `Lean/Elab/Frontend.lean` | 6,094 | 0 |

One difference is intentional. A node's kind used to be rendered through Lean's
`Name.toString`, which escapes anything that is not an identifier, so a `:` token
came out as `«:»`; the views report the name as Lean stores it, so the same token
is `:`. Nothing else about the tree changed — same shape, same spans, same text,
same `missing` flags, node for node.

## Also gone: the truncation budgets

Serialising a tree is expensive, so the old wrapper bounded it: at most 400,000
nodes and at most 96 levels of nesting, with everything past that silently
dropped. Reading the tree costs nothing per node, so those budgets are gone and a
large or deeply nested file now comes back whole. (The file measured here stayed
inside both, which is what makes the record-by-record comparison above exact.)

## Reproducing

After:

```bash
cd crates/lean4-ast
LEAN4_AST_SYSROOT=~/.elan/toolchains/leanprover--lean4---v4.36.0-rc2 \
  cargo run --release --example bench -- 5
```

Before — the same harness against the parent commit (`be61d12`), which is the
code this change replaced:

```bash
git worktree add /tmp/lean4-ast-before be61d12
cd /tmp/lean4-ast-before
python3 build.py --tag v4.36.0-rc2 --skip-tests
```

then drop in a `crates/lean4-ast/examples/bench_before.rs` that is the same
harness written against the old API:

```rust
// parse: Lean serialises the tree, Rust parses the JSON back into a FileAst
let start = Instant::now();
let file = parse(ParseRequest { path: "Bench.lean", source: &source, imports: &[] })?;
let parse = start.elapsed();

// traversal: identical walk, over the materialised nodes
let mut pending: Vec<&Node> = file.nodes.iter().rev().collect();
while let Some(node) = pending.pop() {
    // hash the kind with `«»` stripped (see "Was the tree actually the same?"),
    // the span, the text and the `missing` flag, exactly like the new harness
    for child in node.children.iter().rev() { pending.push(child); }
}
```

and run it with the same arguments. Everything else — the generator, the digest,
the RSS sampling (`/proc/self/statm`, `VmHWM`), the round count — is identical.
